# 模块化评估

现在只有一个 `app` Gradle 模块，按包分层：`core`（通用网络、界面组件）、`domain`（模型、算法、仓库接口）、
`data`（数据库、网络、仓库实现）、`feature`（页面与 ViewModel）。层间依赖方向由 `DependencyRulesTest` 检查，基线已清空，
页面层不直接引用数据库和网络接口。

## 结论：暂不拆模块

| 拆分的收益 | 现状 |
| --- | --- |
| 编译加速 | 改动一个文件后的增量编译主要耗在 KSP（Room、Hilt）和 Compose 编译上；只有一个开发者，并行编译收益有限 |
| 强制依赖方向 | 已由架构测试保证，违反时测试失败 |
| 算法复用 | 口味算法、跨源匹配是纯 Kotlin，已经不依赖 Android；目前没有第二个使用方 |

拆模块的代价：Hilt 绑定和 Room 实体要跨模块可见，`internal` 可见性需要大面积改成 `public`，构建脚本和 CI 也要跟着改。

## 以后真要拆时的顺序

1. **先抽 `:domain`（纯 Kotlin / JVM 模块）**：`domain` 包已经不引用 `android.*` 和 `data.*`（架构测试保证）。
   抽出来后算法单测不再需要 Android 插件，跑得更快，也可以单独给评测脚本用。
   前提：把 `domain` 里用到的少量 `core.common` 类型（`AppResult`、`AppError`、协程工具）一起移到一个 `:core-common` 纯 Kotlin 模块。
2. **再抽 `:data`**：Room、Retrofit、Hilt 模块放进去，`app` 只依赖接口。
3. **最后才考虑按页面拆 `:feature-*`**：只有页面数量和协作人数明显增加时才值得。

触发条件（满足任一再动手）：干净构建超过 10 分钟、增量构建经常超过 1 分钟、有第二个模块需要复用 `domain`、多人同时开发同一区域频繁冲突。
