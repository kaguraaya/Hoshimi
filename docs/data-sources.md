# 数据源

本文说明每个数据源在应用里的用途、回退方式和缓存策略。限流数值见 [rate-limits.md](rate-limits.md)。

## 1. 各数据源的用途

| 数据源 | 用途 | 远端代码 |
| --- | --- | --- |
| Bangumi（`api.bgm.tv`） | 主数据源：作品标题、简介、标签、封面、Staff / 角色 / 声优、短评、关联作品；每日放送；收藏与评分同步；待补池写回「想看」；OAuth 登录 | `data/remote/bangumi` |
| AniList | 评分；放送表的精确时刻匹配；公共缓存补充 | `data/remote/anilist` |
| Tenrai | 默认的 MyAnimeList 评分来源；放送表仍缺时刻时查询本季数据；公共缓存补充 | `data/remote/tenrai` |
| MyAnimeList 官方 API | 可选，需要用户自己的 Client ID；评分与搜索 | `data/remote/mal` |
| VNDB（Kana API） | 视觉小说详情；匹配到 Bangumi 条目后同时显示 Bangumi 资料与评分 | `data/remote/vndb` |
| Jikan | 只在「设置」的连接测试里使用，不参与详情、探索、画像、榜单或缓存补充 | `data/remote/jikan` |
| AI 服务商 | 无剧透评价、AI 口味匹配、标签细分；只发往用户配置的服务商 | `data/remote/ai` |

- Bangumi 是作品资料的唯一来源。其它平台的数据只补充评分和时刻，不覆盖 Bangumi 的标题、简介、标签或封面。
- 跨源匹配在 `domain/matching`：按规范化标题与媒介类型聚类，按可信度与评分人数选代表条目，避免同名小说或视觉小说抢占动画的评分。
  - 外站大多只有日文原名、罗马音和英文名。Bangumi 条目会从信息框读取「别名」等字段（通常有英文名、罗马音），和外站的名字直接比对。
  - 给 Bangumi 作品补外站评分时，查询词依次用原名、罗马音、英文名和较长的拉丁字母别名，不用中文名和拉丁字母简称；
    先搜 Bangumi / AniList，再用 AniList 命中条目的罗马音和英文名去搜 Tenrai / MAL。
  - 续作不合并：识别「第2期 / 2期 / 第2クール」「Season 2 / 2nd Season / S2」「2ndシーズン」、罗马数字（II–V）和「続」。
  - 衍生条目不合并：外传、剧场版、OVA、特别篇、总集篇、完结篇、主题曲 / 无字幕 OP·ED / MV、PV / CM / 预告、迷你动画、映像特典。
    季度与衍生标记只看正式标题，不看别名（别名里常有「OP」这类简称）。
  - MAL 体系（Tenrai / Jikan / MAL）的 Music、PV、CM 条目与 AniList 的 MUSIC 格式归为「其他」，不参与动画匹配和推荐。
- 每个数据源都可以在设置里单独关闭。

## 2. 详情页

1. 先显示数据库里的缓存（作品、评分、Bangumi 扩展资料），过期后在后台刷新（`DetailRepositoryImpl.observeBangumiExtras`）。
2. 条目、人物、角色请求并行发出；同一作品 60 秒内的重复请求合并（`RequestCoalescer`），前台请求不等待后台请求。
3. 其它平台的评分只补缺失或过期的部分：已关联的平台直接按 id 取，未关联的按标题去 AniList、Tenrai（以及配置了的 MAL）搜索匹配。
4. 下拉刷新（`DetailViewModel.onPullRefresh`）强制刷新评分、条目资料与标签、自己的 Bangumi 记录（视觉小说另刷新 VNDB 详情），
   随后刷新角色 · Staff / 关联作品；条目请求带 `Cache-Control: no-cache` 并跳过 60 秒结果复用（`fresh = true`）。
   不重新调用 AI，雷达和 AI 分析保持原样。

### 下拉刷新

只放在用户期待下拉能拿到新内容的页面，统一用 `AcgPullRefreshBox`（`core/designsystem`）。`RefreshGate` 让指示器最多转 3 秒、
至少转 0.6 秒，超时后刷新继续在后台完成（页面观察数据库，数据到了自动更新）；30 秒内重复下拉不会重复请求网络：

| 页面 | 下拉做什么 |
| --- | --- |
| 首页 | 本季列表（Bangumi 每日放送按评分人数排 + 本季排行一页，`WorkRepository.refreshHomeSeasonal`）和近期放送，并行、前台优先级、跳过 HTTP 缓存；**不**同步收藏，也不跑整套公共缓存补充 |
| 发现 · 榜单 | 重新拉当前范围首页（列表保持显示） |
| 发现 · 为你排行 | 在本地作品库上重新计算口味排行，不联网 |
| 发现 · 评分差异 | 公共池（后台优先级），再补一轮第二平台评分 |
| 发现 · 搜索 | 当前关键词重搜（搜索框为空时不响应） |
| 作品详情 | 见上 |
| 视觉小说榜单 | 与顶栏刷新按钮相同 |
| 我的库 | 同步 Bangumi 收藏（与「我的」页同步按钮相同） |

「我的」页已有同步按钮；待补池、时光机、口味、探索队列、设置等页面的内容在本地生成，不提供下拉。

## 3. 放送表

首页「本季新番 / 本季热门」来自 `refreshHomeSeasonal` 存下的两个有序列表（`HomeSeasonalLists`，读法同榜单缓存）：
打开首页时先显示上次存下的列表，再在后台取一次（一小时内走 HTTP 缓存）；列表为空（首次打开且离线）时退回本地作品库里最新的作品。
首页不按评分或人数排序：从两个列表里「评分人数前一半（至少 12 部）」和「口味匹配度 ≥ 72%」的作品中随机挑 6 部，
下拉刷新取到新数据后马上换一批并提示（不等写库）；打开首页时只把已显示作品的评分换成最新的，不突然换一批。
卡片显示 Bangumi 评分和评分人数，标题旁显示上次联网取到的时间。发现页榜单下拉提示名次或评分的变化。
网络结果一到就先显示（`onFetched` 回调），再写数据库：写库要和后台补资料排队，等它会让页面晚几秒才变。
发现页榜单（`loadBangumiRankingPage`）同理。首页数据流任何一路出错时按 1 / 2 / 4 秒重试三次，仍失败时保留上次的内容并提示，
从没成功过才显示错误页；错误页可以下拉或点「重试」重新订阅。
`/calendar` 响应带 `max-age=3600`，下拉刷新和强制刷新放送表时带 `Cache-Control: no-cache`，否则一小时内拿到的都是 HTTP 缓存。

先查 Bangumi 每日放送，再用 AniList 做高置信度的时刻匹配；仍缺具体时刻时才查 Tenrai 本季数据。
首页的放送数据缓存 30 分钟，周视图 6 小时，Tenrai 本季结果在进程内缓存 6 小时（`BroadcastScheduleRepositoryImpl`）。
缺少精确时刻时显示 Bangumi 的星期信息。

## 4. Bangumi 收藏同步

`BangumiSyncManager.syncCollections`：

- 首页、我的、时光机、口味分析和后台自动同步（`BangumiSyncWorker`）可能同时触发，同一时间只跑一次，后来的调用共享正在进行的那次结果；
  同步在管理器自己的作用域里运行，发起页面离开不会中断它。
- 开始前按需续期 OAuth token（`BangumiTokenRefresher`，剩余少于 3 天时续期），后台自动同步也能保持登录。
- 分页拉取全部收藏（每页 50 条，最多 1 万条）；`getMe` 和每一页遇到网络、超时、服务端错误或限流时，间隔 2 秒、5 秒各重试一次。
- 网络类失败的提示会说明 API 与网页走不同线路，并指向「设置 → 数据源 → Bangumi → API 地址」。
- 自动同步默认关闭，在「设置 → 同步」选择间隔（WorkManager 下限 15 分钟，需联网）；
  临时失败最多重试 3 次，鉴权失效等再试也不会成功的失败不重试，等下一个周期。
- 合并以较新的一方为准（`CollectionMergePlanner`）：比较 Bangumi 条目的 `updated_at` 与本地记录的 `updatedAt`；
  本地 `updatedAt > syncedAt` 表示改了还没推送。本地较新 → 交给待推送队列推上去；网页较新 → 覆盖本地。
- 只有拉取完整（没有失败的分页）时才判断「网页上删了」：本地记录曾在 Bangumi 上出现过（`sourceUpdatedAt` 不为空）、
  已同步、这次没有出现 → 移进回收站（原因「Bangumi 上已删除」），不直接删除。
- 在应用里移除的收藏留一个本地标记；网页上那条在移除之后没再改过，同步时就不会把它加回来；网页上更晚改过则以网页为准恢复。
- 换账号：记下上次同步的用户名（`lastSyncedBangumiUser`，退出登录不清除），发现用户名变了就暂停同步，
  由界面询问「合并到新账号 / 旧账号的收藏移到回收站 / 稍后再说」（`BangumiSyncManager.resolveAccountSwitch`）。

## 4a. 删除、回收站与待推送

Bangumi 公开 API 没有删除收藏的接口，修改收藏也不能写日期（`bangumi/api` 的 `open-api/v0.yaml`），所以：

- 移出待补池、清空收藏记录都先进回收站（`trash_items` 表，数据库版本 20），保留 30 天，可撤销 / 恢复；
  恢复后加入时间、状态、评分、短评都是原值。回收站只在本机，不同步。
- 在应用里移除不会改网页：网页上那条收藏保持原样，日期也就保持原样；回收站里给出「去网页移除」链接。
- 撤销提示条在根部统一显示（`UndoController` → `AppShellViewModel`），一次批量移除一起撤销。
- 待推送队列（`BangumiOutbox`）不另建表：所有 `updatedAt > syncedAt` 的 Bangumi 收藏逐条推送；推送前先查网页上这条的
  `updated_at`，网页更晚改过就以网页为准、不推送。推送中用户又改了这条，会保留「未同步」下次再推。
  `BangumiOutboxWorker` 需要联网，失败按指数退避最多重试 5 次；应用启动、详情页保存失败、恢复回收站记录时都会排一次。

## 4b. 数据库升级与自动备份

- **升级前备份**（`DatabaseUpgradeBackup`）：Room 打开数据库之前读数据库文件自己的 `PRAGMA user_version`，
  低于当前版本就把数据库文件连同 `-wal`、`-shm` 原样复制到 `files/db-backups/v{旧版本}-{时间}/`，附 `meta.json`（核心表行数），
  最多保留 2 份；可用空间不足 3 倍时跳过。
- **升级后自检**（`DatabaseHealthMonitor`）：启动时打开数据库，开屏保持到自检结束。
  打不开 → 界面换成安全模式（导出升级前备份、用升级前最近的自动备份重新开始、或等待修复版本）；
  刚升级过 → 对比核心表行数，某张表比升级前少了 10% 以上（原来至少 10 行）就提示可以用自动备份补回。
- **自动备份**（`AutoBackupManager`）：与「导出备份」相同的 JSON（与数据库结构无关，不含凭据），写到 `files/auto-backups/`，保留 3 份。
  先写临时文件，读回解析成功才改名；每次结果（成功时间 / 失败原因）记在设置里，「设置 → 备份与导出 → 数据安全」可见。
  默认开启：WorkManager 每 7 天一次（电量不低时），另外应用启动时超过 7 天没成功就立即补做，升级自检通过后也立即备份一次。
  升级后疑似少了数据时暂不自动备份，避免挤掉升级前的好备份。

**线路**：Bangumi 官方 API 只有 `api.bgm.tv` 一个生产域名（经 Cloudflare），没有官方备用线路；`api.bgm38.tv` 是数据会重置的开发环境，
`next.bgm.tv` 是新版网页的私有接口，没有兼容性保证。网页 `bangumi.tv` 不经 Cloudflare、也不提供 API，所以会出现网页能打开而 API 连不上的情况。
应用支持在设置里换成社区反代或自定义地址；非官方地址默认不发送个人 Token，需要用户确认风险。
HTTP 客户端开启了 15 秒一次的 HTTP/2 心跳，长连接被中途掐断时会关闭重建，避免请求一直卡在死连接上。

## 5. 缓存与失败处理

- HTTP 缓存在 OkHttp 层，限流拦截器排在缓存之后（`NetworkModule.networkInterceptors`），命中缓存的请求不占限流额度。
- 收到 `429` / `503` 后，同一数据源的全部请求按 `Retry-After` 一起退避，不重试同一个请求。
- `429`、`503`、`504`、DNS、TLS、连接或读取失败只进入冷却并保留旧值，不写入「无评分」负缓存。
- 补充源不可用时，详情页保留 Bangumi、AniList 和本地缓存，渐进展示，不自动换用 Jikan。
- 作品资料（`work_features`）长期保存，「缓存管理」里的清理不会删除；它是口味算法的输入，见 [taste-algorithm.md](taste-algorithm.md) §2。

## 6. 后台任务

都用 WorkManager，执行时间由系统决定；请求都标为 `RequestPriority.BACKGROUND`，给前台让路。

| 任务 | 作用 | 规模 |
| --- | --- | --- |
| `WorkFeatureEnrichmentWorker` | 先把收藏与待补池的作品补成完整资料，再给本地作品库里没有资料的动画补基础资料 | 每批 20 / 40 部，有进展且有剩余才排下一批 |
| `RatingBackfillWorker` | 给只有一个平台评分的动画补其它平台评分（开关在「设置 → 推荐与口味」，默认开启） | 每次最多 20 部，约 6 小时一次；同一部 7 天内不重复查 |
| `BangumiWishSyncWorker` | 把加入待补池的作品写成 Bangumi「想看」：先查询已有状态，已有任何状态就跳过 | 队列式，失败指数退避重试 |
| `BangumiOutboxWorker` | 推送本地改了还没推到 Bangumi 的收藏，见 §4a | 单次任务，需联网，最多重试 5 次 |
| `AutoBackupWorker` | 每周自动备份，见 §4b | 7 天一次，最多重试 3 次 |
| 公共缓存补充 | 从榜单分页补充公共作品缓存（可在缓存管理里关闭） | 分页，受限流约束 |
| `TasteProfileAutoUpdater` | 收藏变化后只读缓存重建口味画像，缺资料的作品后台补齐 | 每批 40 部 |

## 7. Jikan 与 Tenrai 的选择依据

2026-08-09 在同一网络下以只读请求实测：

| 服务 | 搜索 | 本季 | 榜单 | 耗时 |
| --- | --- | --- | --- | --- |
| Tenrai `v1` | 200 | 200 | 200 | 约 2.3–4.8 秒 |
| Jikan `v4` | 504 | 504 | 504 | 约 1.7–2.0 秒后返回网关错误 |

Jikan 的 `504` 表示它连不上 MyAnimeList，不是本地网络问题；社区 issue [jikan-me/jikan#596](https://github.com/jikan-me/jikan/issues/596) 记录了同类失败。
因此 MAL 评分默认取自 Tenrai（文档 <https://api.tenrai.org/documentation>，适配端点 `anime`、`anime/{id}`、`top/anime`、`seasons/now`，DTO 允许服务新增字段）。
如果以后要恢复 Jikan，先重新核验它的服务状态。

## 本地作品库的来源

口味排行、匹配度参照用的是 `work_features`（作品的社区标签和标注人数、评分、集数、平台、封面等）。作品进库有三条路：

1. 个人收藏同步时带回的资料，后台再补全 Staff、角色（`WorkFeatureEnrichmentWorker`）；
2. 搜索结果和榜单（`POST /v0/search/subjects`）本身就带完整的标签和标注人数，`BangumiRemoteDataSource` 把结果交给
   `BangumiSubjectSink`（`LocalPoolSubjectSink`），在后台存成基础资料，不额外请求；已有更完整资料的作品不会被降级；
3. 其它只存了作品行、还没有资料的作品（同步评分、放送表、榜单等带进来的），由补资料 Worker 每批 40 部补基础资料。

补资料 Worker 的顺序：个人收藏 / 待补池补完整资料 → 作品池里没有资料的补基础资料 → 其余基础资料再补完整。
只有基础资料的公共作品永远不少，所以必须排在「没有资料」之后，否则没有资料的作品一直轮不到。

口味排行页的「补充作品库」（`LocalPoolExpander`）按 Bangumi 排行一段段取条目（每段 100 部、接口每次 20 部），
只把结果里的标签、评分等写进 `work_features`，不走作品表的整套写库；在应用级协程里跑，离开页面也继续，
记下补到第几名（`localPoolExpandOffset`），下次接着往后补，排行到底后从头再来。排行结果按画像和动画资料部数缓存，
作品库变大后再打开会自动重算。

## 番剧回顾的数据

「我的 → 分享与回顾 → 番剧回顾」（`WatchReportRepositoryImpl`，只读本地）：本地收藏里状态为「看过」的作品，看完时间按顺序取
时光机记录的「状态变成看过」的时间 → Bangumi 收藏更新时间 → 本地更新时间；弃番同理。标题、封面、年份来自作品表，社区评分来自评分表，
题材（`TasteTagTaxonomy.isSelectableGenre`）、集数和单集时长来自作品资料，时长缺失按 24 分钟算。时间范围按动画季（1 / 4 / 7 / 10 月）或自然年。
分享图（`ReportImage`，1080×1920）有封面墙和前十榜单两种版式，带项目二维码；封面用 Coil 关闭硬件位图下载后再画，存进相册后可直接分享。
